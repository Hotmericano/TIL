# Git 협업 흐름과 배포

## 오늘 한 것
- dday-calculator를 v0.2부터 v1.1까지 개발하고 GitHub Pages로 배포했다.

## 머지 충돌 (Merge Conflict)
- 언제 생기나: 두 브랜치가 같은 파일의 같은 부분을 서로 다르게 수정해서, 깃이 어느 쪽을 남길지 스스로 정할 수 없을 때. 같은 파일이라도 서로 다른 줄을 고쳤으면 깃이 알아서 합쳐준다.
- 충돌 표시 `<<<<<<<`, `=======`, `>>>>>>>`의 의미:
  - `<<<<<<< HEAD` ~ `=======`: 현재 브랜치 쪽 내용
  - `=======`: 두 쪽을 나누는 구분선
  - `=======` ~ `>>>>>>>`: 합치려는 브랜치 쪽 내용
- 해결 방법: 둘 중 원하는 쪽을 선택하거나 둘을 섞어서 새로 쓰고, 마커(`<<<<<<<`, `=======`, `>>>>>>>`)를 모두 삭제한 뒤 커밋한다.
- 실수한 것: 충돌 표시를 지우지 않고 커밋해서 main에서 사이트가 동작하지 않았다.
- 다음부터: 커밋 전에 `Ctrl + F`로 `<<<<<<<` 검색하기

## 브랜치 정리
- 머지한 브랜치는 지워도 되는 이유: 브랜치는 이름일 뿐, 커밋 자체는 남아있다. 브랜치의 커밋들이 main에 들어가있음. 즉, 커밋은 main의 기록 안에 그대로 남는다.
- 지운 브랜치를 되살리는 방법: 머지된 PR 페이지에 Restore branch 버튼

## 이슈 닫기
- 삭제: 이슈 자체가 완전히 사라진다. 복구가 안 되고 관리자만 할 수 있다.
- Close as completed: 해결해서 닫음 (보라색)
- Close as not planned: 안 하기로 해서 닫음 (회색). 기록이 남고 다시 열 수 있다.
- 그래서 보통은 삭제 대신 닫는다. 왜 안 하기로 했는지도 기록으로 남기 때문.

## PR 설명 쓰는 법
- 변경 사항 / 변경 이유 / 테스트 / `closes #번호`
- 제일 중요한 부분과 그 이유: 뭘,왜,어떻게 확인했는지
- PR을 올린 뒤 같은 브랜치에 커밋하면: PR은 브랜치를 합치자는 요청임. 즉 브랜치에 커밋이 늘어나면 PR에도 그대로 반영됨.

## GitHub Pages
- 사이트 주소 형식: `아이디.github.io/저장소이름`
- 배포되는 시점: main에 커밋이 들어갈 때(머지할 때) 자동으로 배포되고, 사이트에 반영되기까지 1~2분 걸린다.
- PR 화면의 "This branch has not been deployed"의 의미: 이 브랜치는 배포된 적이 없다. dday-calculator는 main 브랜치만 배포되기 때문에 main에 머지하면 자동배포됨.

## localStorage
- 무엇인가: 브라우저에 작은 데이터를 저장해두는 공간, 새로고침하거나 다시 열어도 유지됨
- 특징 (어디에 저장되나, 언제 사라지나): 그 브라우저에만 저장됨 (휴대폰과 PC는 따로 기억함, 서버로 가지 않음). 브라우저 기록이나 사이트 데이터를 지우면 같이 사라짐.
